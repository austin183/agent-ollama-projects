# Documenting Container Experiments

Document experiment results, write READMEs, and clean up generated artifacts.

## When to Document

Use a tiered approach based on experiment stage:

- **experiment-timeline.md:** Can be updated iteratively during build and execution. Experiments often span multiple sessions; record iterations, dead ends, and partial progress as they happen.
- **README.md:** Must wait until the experiment is working end-to-end. Premature README verification commands and expected output become misleading. Write the README only after confirming everything works.

## Order of Operations

```
build -> execute -> document
```

The timeline can be written during build/execute, but the README is the final step.

## experiment-timeline.md

The timeline is per-experiment and lives in the experiment directory. It captures the full journey, including failures and course corrections.

### How to Write

- **Date, status, and machine context** — Note whether running on "ASUS TUF" or "Dell Inspiron" (or other machine). Machine context is inline, not in a separate file.
- **Iteration log** — For each attempt, record:
  - Approach and what was tried
  - Issues encountered
  - Root cause analysis
  - Resolution or why it remains unresolved
- **Verification results** — Pass/fail with actual output, not just "passed"
- **Key learnings and design decisions** — What worked, what to do differently next time
- **Append, don't overwrite** — On re-runs, add new entries below existing ones. The timeline is a historical record.

### Example Entry

```markdown
## 2026-05-01 — ASUS TUF — Iteration 3: Working

**Approach:** Switched healthcheck from `wget` to `curl` after discovering the image lacks wget.

**Issues:**
- Healthcheck failed with `/bin/sh: 1: wget: not found`
- Root cause: Alpine-based image uses curl, not wget

**Resolution:** Updated healthcheck to use `curl -sf http://localhost:8080/health`

**Verification:**
- Container status: healthy
- DNS resolution: pass (`nslookup main-service` resolved correctly)
- HTTP health: pass (curl returned 200 with `{"status":"ok"}`)

**Learnings:**
- Always check which HTTP tools are available in the image before writing healthchecks
- The `which curl wget` command is a quick way to verify
```

## README.md

Write the README only after the experiment is working end-to-end. Base all content on what actually worked, not assumptions.

### Required Sections

1. **Overview** — 1-2 sentence summary of what the experiment does
2. **Services table** — Service | Port | Purpose
3. **Quick Start** — Exact commands to launch, including any prerequisite steps (directory creation, env file setup)
4. **How It Works** — Service architecture and data flow
5. **Testing** — Verification commands with expected output based on *actual* working commands
6. **Troubleshooting** — Common pitfalls and fixes encountered during this experiment
7. **Cleanup** — How to shut down and remove all data, including generated files (see below)

### Writing Verification Commands

- Use the actual commands that worked during execution, not assumed ones
- Include actual expected output from a successful run
- Note any service-specific quirks (e.g., "this image uses curl, not wget")

## Cleanup of Generated Files

The README's Cleanup section should document any files or directories generated by the experiment that would cause failure on a fresh run.

### What to Document

- **Wizard-generated configs** — Files created by setup wizards (e.g., `conf/AdGuardHome.yaml`). These may need removal or regeneration.
- **Pre-created directories** — Directories that must exist before launch (e.g., `mkdir -p work conf`). Call these out in Quick Start so first-time users don't fail.
- **Initialized database data** — If bind mounts are used for database storage, initialized data will prevent re-initialization scripts from running. Document that `down -v` or manual cleanup is needed.
- **Runtime-generated files** — Any files created during execution that affect subsequent runs.

### Guiding Principle

Document anything the README or compose steps generate on their own that would cause a first-time reader to fail. If a reproducer follows the README exactly and hits an error due to missing cleanup, the Cleanup section is incomplete.
