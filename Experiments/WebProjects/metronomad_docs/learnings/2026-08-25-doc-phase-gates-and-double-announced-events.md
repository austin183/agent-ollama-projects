# Doc-phase mechanical gates can contradict the phase's own prose — and one event pinned to two status surfaces double-reads to screen readers

**Date:** 2026-08-25
**Context:** Metronomad CR 001 Phase 7 (docs + acceptance). Two things happened that no test could have surfaced, both resolvable only by knowing which artifact is authoritative:

1. **A phase file instructed text its own success criterion forbade.** Phase 7's Changes section says the AGENTS.md Directory note should "note `#offsetScrubber`'s replacement by the canvas slider" — but the phase's Automated success criteria require `rg "offsetScrubber" index.html test/ MyComponents/ MyESModules/ Metronomad/AGENTS.md` → **zero hits**. Writing the prose as instructed would fail the gate; satisfying the gate as worded would drop the note entirely. Neither instruction was wrong in isolation — the phase simply never checked the two against each other.
2. **The final whole-change-set world-review confirmed the Phase-6 UX-6 discussion item is an emergent property of pinning one event to two announcement surfaces** — the tempo prefill both inserts a visible hint `<p role="status">Detected ~N BPM</p>` and sets the polite live region to "Detected tempo N BPM". A screen reader reads both. No unit row, E2E row, or per-phase review flagged the *combination*; only the cross-surface view (and ultimately the manual SR pass) sees it. KB-12 covers the opposite failure (rapid *succession* coalesced by AT) — this is a single event read twice via two channels, and nothing in the existing learnings/skill covered it.

## Rules

1. **In any docs phase, dry-run every mechanical gate (grep passes, integrity checks, token contracts) against the PLANNED wording before writing.** The gates are success criteria — on a conflict between the phase's Changes prose and its success criteria, the success criterion wins, and the prose's *intent* is expressed in a token-free form. Here: AGENTS.md says the canvas "replaced the old offset range input (the app now has zero `input[type=\"range\"]`)" — which also matches E2E-3.10's count-0 assertion, so the note survives *stronger* than the literal token would have. Record the resolution in the phase-map status line so the next reader doesn't re-litigate it. (Historical references to a retired identifier in files *outside* the gate's scope — e.g. KB-17 in the v1 context.md explaining the v1-era precedent — are fine and should stay.)
2. **When a spec/CR pins the same user event to two announcement surfaces — a visible `role="status"` hint *and* a live-region announcement — expect a screen-reader double-read, and make that expectation explicit at CR-expansion time.** The checklist to run at CR/plan time: does this event set `announcement` (live region) AND insert/toggle a `role="status"` element? If yes, (a) add a manual dual-SR acceptance item that names the double-read by string, (b) pre-decide the remedy path — one pinned surface yields, which is a **CR-level spec change**, never an in-plan markup edit, and (c) note it is a different failure mode from KB-12-style coalescing so a future reviewer doesn't "resolve" it by debouncing. The UX-6 disposition in CR 001 (discussion item routed to Phase 7, remedy = CR change) is the template.
3. **A final whole-change-set review after clean per-phase reviews is cheap insurance for exactly two things per-phase reviews don't own: the docs delta itself, and cross-phase integration surfaces** (memory across repeated loads, independent async tasks racing, draft state vs state-machine transitions). Brief it with the pinned-decision inventory (D-*/W-*/KB-*/scenario IDs) and the prior per-phase review history inlined — CR 001's final pass produced line-by-line doc-vs-source verification and zero action items instead of re-litigating settled decisions.

## Why it matters

Rule 1 failure mode: the builder either ships a doc the phase's own gate fails (silent plan breakage caught only at close-out) or silently deletes the instructed note (lost knowledge — the fact that the range scrubber was *replaced* is exactly what future readers need). Rule 2 failure mode: the double-read is discovered by a user with a screen reader after ship, at maximum trust cost, with no pre-decided remedy. Rule 3 failure mode: each phase review is clean, the plan closes, and a cross-surface defect (or a doc drift) ships with a green board.
